# План перехода интерфейса Valetudo на Vue 3

## Цель и границы

Заменить текущий React/MUI интерфейс на Vue 3 + TypeScript + Vite + Tailwind CSS и перенести визуальное направление из `preview.html`. Критерий готовности — функциональный паритет с действующим интерфейсом для всех поддерживаемых конфигураций роботов, а не сходство с демонстрационным прототипом. Backend API, форматы команд и карты, SSE, адреса страниц и размещение готовой сборки не менять без отдельной причины.

Прототип служит источником компоновки, навигации, цветов и мобильного сценария. Его SVG-карта, демонстрационные значения и локальные команды не являются реализацией. Не добавлять как существующие возможности историю отдельных уборок, выбор этажей, профиль пользователя, глобальное число повторов и переключатель доставки уведомлений: для них не подтверждены API и хранение данных.

## Стек и решения

| Слой | Решение |
| --- | --- |
| Приложение | Vue 3, SFC с `<script setup lang="ts">`, Composition API; `@vitejs/plugin-vue` в существующей конфигурации Vite. |
| Маршруты | Vue Router с `createWebHashHistory`; сохранить пути `/#/`, `/#/robot/*`, `/#/options/*`, `/#/valetudo/*` и поведение прямой ссылки/обновления страницы. |
| Компоненты | PrimeVue 4 в styled mode с собственным preset из дизайн-токенов; индивидуальные импорты. Диалоги, поля, переключатели, меню, уведомления и таблицы брать из библиотеки. Карту и крупные продуктовые композиции делать своими компонентами. |
| Стили | Tailwind CSS 4 через `@tailwindcss/vite` для сеток, отступов и адаптивности; семантические CSS-переменные для темы. Проверить порядок CSS-слоёв и интеграцию `tailwindcss-primeui` в техническом spike до массовой верстки. |
| Данные | Сохранить типы, `client.ts`, преобразование карты и транспорт Axios/SSE как независимый от UI слой. React hooks заменить на `@tanstack/vue-query`; локальное состояние карты/навигации вынести в composables, Pinia добавлять только для реально разделяемого состояния. |
| Сборка | Сохранить `base: "./"`, `frontend/build`, `static`, Vite proxy `/api`, `/_ssdp`, `/_killswitch`, целевую совместимость браузеров и сценарий `npm run watch --workspace=frontend`. |

В начале проверить совместимость версий TypeScript, `vue-tsc`, `@vitejs/plugin-vue`, Tailwind и PrimeVue: в корне сейчас TypeScript 4.8.4. Обновление TypeScript провести вместе с проверкой backend, а не только frontend.

## Контракты, которые должны пережить миграцию

1. `/api/v2` и относительные URL; cookie/HTTP auth, ошибки запросов, повторная загрузка, признак изменения backend по `x-valetudo-commit-id`.
2. SSE карты, атрибутов, событий и других текущих подписок: повторное соединение, отписка при уходе со страницы, инвалидирование запросов и отсутствие дублирующих соединений.
3. Проверка каждой `Capability` отдельно, а также свойств и допустимых диапазонов конкретного робота. Два пресета прототипа не подменяют реальные capability-наборы.
4. Состояния команд Start/Resume/Pause/Stop/Home, подтверждение конфликта с выбранным действием на карте, pending/error и предотвращение повторной отправки.
5. Светлая/тёмная и системная тема, сохранённый ключ `palette-mode`; мобильные жесты и доступность всех функций с клавиатуры.
6. Состояние первичной настройки Wi-Fi на embedded-устройстве, загрузочный экран, fallback при ошибке и недоступном устройстве.

## Этапы

### 0. Зафиксировать базу и матрицу паритета

- Собрать реестр из текущих `AppRouter`, вложенных router-файлов, меню, компонентов и API: маршрут, условие показа, запросы, команды, подтверждения, loading/error/empty.
- Для каждого пункта указать реализуемый Vue-экран и проверку. Отдельно описать профили: минимальный робот, сегменты/зоны/точка, моющий робот, док, камера, Wi-Fi/embedded.
- Снять снимки действующего UI на широком и узком экранах, в обеих темах, включая диалоги, карту и системные состояния. Это база для сравнения внешнего вида и поведения.
- Разметить все элементы прототипа как «действующая функция», «только оформление» или «новая функция с отдельным backend-контрактом».

**Выход:** утверждённая матрица паритета; нет пунктов меню без владельца/экрана.

### 1. Параллельный каркас Vue

- Создать временный npm workspace для Vue-сборки, не переключая backend на неё; затем при выпуске разместить итоговую сборку в `frontend/build` и обновить корневые скрипты. Не вести две продакшен-сборки после переключения.
- Настроить Vite, TypeScript/`vue-tsc`, ESLint для Vue, hash-router, Vue Query, PrimeVue, Tailwind, шрифты и иконки.
- Перенести независимые типы, API-клиент, SSE, query keys и мутации; оформить composables с едиными правилами инвалидирования и сообщений об ошибках.
- Сделать оболочку, первичную настройку Wi-Fi, загрузку capability-набора, темы, меню, события и маршруты.

**Выход:** Vue-приложение открывается с действующим backend, проходит авторизацию и обновление страницы по прямому hash URL; React-интерфейс ещё остаётся рабочим.

### 2. Дизайн-система и навигация

- Перенести дизайн-токены прототипа: цвета, поверхности, типографику, радиусы, тени, сетку, размеры целей касания. Настроить PrimeVue preset и единый переключатель темы.
- Сделать компоненты `AppShell`, `PageHeader`, `SettingsGroup`, `ActionCard`, `StatusBadge`, `ConfirmAction`, `AsyncState`; скрывать неподдерживаемые действия по capabilities.
- Реализовать десктопную и мобильную навигацию со всеми существующими разделами. Пункты «История» и «Этаж» заменить на подтверждённые функции или убрать. Не оставлять декоративных кнопок без действия.
- Проверить фокус, клавиатуру, подписи полей, контраст, состояния hover/focus/disabled/loading и безопасную область мобильного экрана.

**Выход:** все существующие маршруты достижимы, даже если содержимое ещё переносится по этапам.

### 3. Главный экран и карта — критический путь

- Разделить `BaseMap.tsx` на независимый движок и Vue-адаптер: lifecycle canvas, resize/HiDPI, слои, анимация, координаты, события мыши/тача, очистка ресурсов. Повторно использовать чистые классы слоёв и структуры, удаляя React-типы из общих частей.
- Восстановить SSE-обновление карты, позицию робота, маршрут, сегменты, зоны, цель, виртуальные ограничения, подписи и адаптацию к теме. Не переносить SVG демо-карты в рабочий экран.
- Реализовать режимы уборки всего помещения, сегментов, зоны и точки с реальными ID/координатами и допустимым числом проходов; выбор и подтверждение отражать на карте.
- Добавить статус робота, заряд, текущую статистику, пресеты режима/мощности/воды, док, насадки и основные команды с исходными правилами доступности.
- На телефоне оставить карту доступной для жестов, а главное действие и контекстные настройки — видимыми без дублирования команд.

**Выход:** каждый доступный в старом UI сценарий уборки работает на реальном API и карте для соответствующей Capability.

### 4. Остальные страницы по функциональным группам

| Группа | Обязательный объём |
| --- | --- |
| Робот | Расходники, ручное управление, общая статистика, камера/поток при поддержке. |
| Карта | Управление картой, переименование/разделение/объединение сегментов, виртуальные ограничения, аннотации, покрытие, spectator, экспорт и сброс с подтверждением. |
| Настройки робота | Все доступные контролы и пресеты, DND, голос/звук, блокировки, ковры/швабра/док, system и quirks; структура зависит от capabilities. |
| Подключение | Авторизация, MQTT, network advertisement, NTP, Wi-Fi и provisioning при наличии capability. |
| Valetudo | Настройки приложения и аналитика, таймеры (создание/изменение/удаление), журнал, обновление, AI, информация, помощь и системные данные. |
| Глобальные действия | События и взаимодействия с ними, внешние ссылки Docs/GitHub/Swagger/Donate там, где они присутствуют в оригинале. |

Для каждого экрана переносить не только форму, но и значения из API, ограничения ввода, dirty/saving/success/error, опасные подтверждения и возврат после действия.

### 5. Проверка, переключение и очистка

- Автоматически сравнить маршруты и capability-гейты со старым UI. Написать точечные тесты на чистую логику команд, преобразование координат, состояние выбора и composables; browser E2E покрыть основные действия, настройки, provisioning и адаптивность.
- Проверить карту мышью и касанием, масштаб/панораму, клики по сегментам, рисование и изменение зон/ограничений; отдельно проверить камеру и ручное управление на доступном оборудовании.
- Прогнать минимальный и расширенный набор capabilities, loading/empty/error/offline, светлую/тёмную темы, мобильный и десктопный размер. Сравнить скриншоты с базой.
- Запустить `npm run lint_all`, `npm run ts-check_all`, `npm run build --workspace=frontend`, backend tests при затронутых общих контрактах; проверить готовую сборку через backend, а не только dev-сервер.
- После закрытия матрицы заменить production frontend, удалить React/MUI и временный workspace, обновить lockfile, скрипты и документацию. Сохранить возможность отката к предыдущей рабочей сборке/коммиту.

## Условия завершения

- Каждый существующий маршрут, пункт меню и API-действие из матрицы доступен или скрыт теми же условиями, что в оригинале; пустых экранов и неработающих контролов нет.
- Карта использует реальные данные и даёт те же действия и жесты; состояния робота и ошибки управляют доступностью команд.
- Одинаковая функция работает на телефоне и компьютере, в обеих темах, с клавиатуры там, где это применимо.
- Готовый `frontend/build` обслуживается текущим backend; запросы, SSE, авторизация, прямые hash URL и provisioning проходят проверку.
- Все проверки проходят; любые сценарии, которые нельзя подтвердить без конкретного робота, перечислены отдельно как непроверенные, а не засчитаны по мокам.

## Основные риски

- **Карта:** `BaseMap` наследуется от `React.Component`; переносить её надо по частям с проверкой геометрии, жестов и очистки подписок. Это самый дорогой участок.
- **Совместимость сборки:** TypeScript 4.8.4 и текущий ESLint-стек могут потребовать синхронного обновления. Сначала выполнить маленький spike с `vue-tsc` и полной проверкой backend.
- **Потоки и задержка управления:** камера, spectator, ручное управление и SSE нельзя оценить по статическому прототипу; нужны реальные проверки.
- **Разнородные роботы:** недоступные настройки не должны появляться из-за общего «расширенного» пресета. Матрица capabilities — обязательный приёмочный артефакт.
